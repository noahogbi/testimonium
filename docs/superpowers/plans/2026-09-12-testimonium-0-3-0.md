# testimonium 0.3.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the two package changes the bulletin-srccheck cutover needs — export `toText`, and stop `node.ts` and `curl.ts` swallowing fetch failures.

**Architecture:** Both changes are additive. Neither moves a verdict. The export widens the public surface by one pure function; the warns add stderr output on a path that previously produced none. The risk in this plan is not the code — it is the documentation, because four sentences in binding specs assert that `toText` is sealed and become false the moment it is exported.

**Tech Stack:** TypeScript, ESM, Node ≥20, vitest, zero runtime dependencies.

**Spec:** `docs/superpowers/specs/2026-09-12-bulletin-srccheck-cutover-design.md` §2 (Half A), §4.1, §4.2.

## Global Constraints

- Node ≥20. Zero runtime dependencies — `package.json`'s `dependencies` must stay `{}`.
- `exactOptionalPropertyTypes` is on. `identity: undefined` is not the same as an absent key.
- `npm pack` must yield only `dist/`. Nothing from `fixtures/`, `docs/`, `test/`, `src/` or `scripts/`.
- **Do NOT run `fixtures/challenge-battery.mjs`** — it rewrites tracked fixtures.
- Never write a literal NUL byte into a file. Use a `"\u0000"` escape and byte-check the file afterwards; this repo has a recorded incident of an escape round-tripping into the raw character.
- `VERSION` in `src/version.ts` and `version` in `package.json` are two files held equal by `test/exports.test.ts`. Change both or the test fails.
- Publishing is NOT part of this plan. It is the owner's to perform, via the OIDC staging pipeline.

### Task 2: `node.ts` and `curl.ts` warn before returning `EMPTY_RESPONSE`

**Files:**
- Modify: `src/fetch/node.ts:24`, `src/fetch/curl.ts:62`
- Test: `test/fetch/rung-diagnostics.test.ts` (create)

**Interfaces:**
- Produces: no signature change. Both rungs keep returning `EMPTY_RESPONSE`; they now emit one `console.warn` first.
- Consumes: nothing new.

**`src/fetch/pdf.ts` is NOT part of this task.** Its catch at `:49` already warns — landed in commit `005330a` — and its message is the format to match:

```
warn pdf rung failed for ${url}: ${e instanceof Error ? e.message : String(e)}
```

An earlier draft of the spec claimed all three rungs were silent. Two are.

- [ ] **Step 1: Write the failing tests**

Create `test/fetch/rung-diagnostics.test.ts`. Each rung gets a test that its failure path warns, with the url and the reason present:

```ts
import { describe, it, expect, vi, afterEach } from "vitest";
import { nodeRung } from "../../src/fetch/node.js";

afterEach(() => vi.restoreAllMocks());

describe("node rung diagnostics", () => {
  it("warns with the url and the reason when the fetch throws", async () => {
    const warn = vi.spyOn(console, "warn").mockImplementation(() => {});
    vi.stubGlobal("fetch", () => Promise.reject(new Error("ENOTFOUND example.invalid")));

    const r = await nodeRung("https://example.invalid/a", {});

    expect(r.rawBody).toBe("");
    expect(warn).toHaveBeenCalledTimes(1);
    const msg = String(warn.mock.calls[0][0]);
    expect(msg).toContain("https://example.invalid/a");
    expect(msg).toContain("ENOTFOUND example.invalid");
  });
});
```

Match `nodeRung`'s real exported name and signature from `src/fetch/node.ts` — the call above shows the intent, not the exact shape. Write the equivalent test for `curl.ts`, driving its failure however that module's own tests already drive it.

Assert on the **url and the reason specifically**, never merely that `warn` was called. A test asserting only the call count stays green if the message is a bare `"warn"`, which would defeat the entire point of this task.
