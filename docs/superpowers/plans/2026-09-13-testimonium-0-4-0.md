# testimonium 0.4.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship TypeScript declarations for the first time, and close four findings carried from earlier releases.

**Architecture:** Nothing here changes a verdict or a runtime value. Two source annotations widen literal types before they can be committed to; nine type-only exports make already-crossing shapes nameable; declaration emit is switched on and verified across three module-resolution modes; the CLI tally becomes importable so its drift can be tested. The rest is documentation.

**Tech Stack:** TypeScript, ESM, Node >= 20, vitest, zero runtime dependencies.

**Spec:** `docs/superpowers/specs/2026-09-13-testimonium-0-4-0-design.md`. Read it before Task 1 — §8 records what review changed, and two sections of it correct claims the first draft made.

## Global Constraints

- Node >= 20. Zero runtime dependencies — `package.json`'s `dependencies` must stay `{}`.
- `exactOptionalPropertyTypes` is on. `identity: undefined` is not the same as an absent key.
- `npm pack` must ship only `dist/` plus standard metadata — nothing from `fixtures/`, `docs/`, `test/`, `src/` or `scripts/`. After Task 3 it will also contain `.d.ts` files, which is the point; nothing else changes.
- **Do NOT run `fixtures/challenge-battery.mjs`** — it rewrites tracked fixtures.
- Never write a literal NUL byte into a file. Byte-check with `node` after writing (python may be absent from PATH); four NUL incidents have already occurred in this project from unicode escapes round-tripping into raw bytes.
- `VERSION` in `src/version.ts` and `version` in `package.json` are held equal by `test/exports.test.ts`. Change both or the suite fails.
- **The runtime export allowlist in `test/exports.test.ts` must not change.** Every addition in this plan is type-only and cannot appear in an `Object.keys` pin. If that test needs editing, something has gone wrong — stop and report.
- **No verdict may move.** No threshold value changes. `THRESHOLDS` stays frozen at runtime.
- Publishing is NOT part of this plan. Do not tag, publish, or push.

### Task 1: Widen `VERSION` and `THRESHOLDS` before anything is committed to

**Files:**
- Modify: `src/version.ts`, `src/classify/thresholds.ts`
- Test: `test/classify/thresholds.test.ts` (extend), `test/exports.test.ts` (extend)

**Interfaces:**
- Produces: `VERSION: string` (not the literal `"0.3.0"`); `THRESHOLDS` whose values type as `number` while still frozen at runtime.
- Consumes: nothing.

**This task MUST land before Task 3.** Declaration emit is off today, so these types are not yet committed to anything. The moment `.d.ts` ships, they are. Spec §2.6: `VERSION` as a literal makes **every future release type-breaking** (`VERSION === "0.5.0"` is TS2367), and `THRESHOLDS` as literals makes **recalibrating the prose floor breaking** — which directly contradicts spec §5, the section recording evidence that recalibration may be needed.

- [ ] **Step 1: Write the failing tests**

In `test/exports.test.ts`, beside the existing VERSION checks:

```ts
it("VERSION is typed string, not a literal - or every release is type-breaking", async () => {
  const { VERSION } = await import("../src/index.js");
  // The runtime assertion is trivial; the TYPE is the subject. A literal type
  // makes this comparison TS2367 "no overlap" and the file stops compiling.
  const other: string = "0.99.0";
  expect(VERSION === other).toBe(false);
  expect(typeof VERSION).toBe("string");
});
```

In `test/classify/thresholds.test.ts`:

```ts
it("THRESHOLDS values are typed number, not literals - recalibration must not be breaking", async () => {
  const { THRESHOLDS } = await import("../../src/index.js");
  // Same shape of proof: comparing against a different number must COMPILE.
  const candidate = 5000;
  expect(THRESHOLDS.minProseChars === candidate).toBe(false);
  expect(Object.isFrozen(THRESHOLDS)).toBe(true);
});
```

Both tests are about types, and `vitest` type-checks the file it runs. If the annotation is missing, `tsc --noEmit` fails on these lines even when the runtime assertions would pass — which is the failure you are looking for.

### Task 2: Export the nine unnameable types, and pin the type surface

**Files:**
- Modify: `src/index.ts`
- Test: `test/type-surface.test.ts` (create)

**Interfaces:**
- Produces: 23 exported types (the existing 14 plus 9), all type-only. No runtime name is added.
- Consumes: Task 1 is independent of this but both precede Task 3.

**The nine, from spec §2.3:** `Evidence`, `Rule`, `HostRule`, `Document`, `Footnote`, `ClaimsFile`, `ClaimEntry`, `Joined`, `BuiltinRung`.

Each is the field, parameter, or return type of something already public, so a consumer receives or supplies the shape and cannot name it. Find each one's defining module with `grep -rn "interface <Name>\|type <Name>" src/` rather than guessing its path.

- [ ] **Step 1: Write the failing pin**

Create `test/type-surface.test.ts`. It reads `src/index.ts` as TEXT and enumerates exported type names — **not** `dist/`, which `npm test` never builds, and which would make this pass vacuously on a clean checkout.

```ts
import { describe, it, expect } from "vitest";
import { readFileSync } from "node:fs";

/** Both export syntaxes. `export { x, type Y }` and `export type { A, B }`
 *  are both in use in src/index.ts, and an earlier sweep that matched only
 *  the first form reported 8 of 14 - an instrument error that looked exactly
 *  like a spec error. */
function exportedTypeNames(src: string): string[] {
  const inline = [...src.matchAll(/\btype\s+([A-Za-z]\w*)/g)].map((m) => m[1]!);
  const blocks = [...src.matchAll(/export\s+type\s*\{([^}]*)\}/g)]
    .flatMap((m) => m[1]!.split(",").map((s) => s.trim()))
    .filter(Boolean);
  return [...new Set([...inline, ...blocks])].sort();
}

const EXPECTED = [
  "BuiltinRung", "CheckOptions", "CitationResult", "ClaimEntry", "ClaimProblem",
  "ClaimsFile", "Document", "Evidence", "FailOn", "Fetcher", "FetcherOptions",
  "FiredRule", "Footnote", "HostRule", "Joined", "RawResponse",
  "ReachabilityOptions", "ReachabilityResult", "Rule", "RuleSet", "RunTally",
  "RungId", "Verdict",
].sort();

describe("public type surface", () => {
  it("exports exactly the pinned 23 types - an addition is as much a change as a removal", () => {
    const src = readFileSync(new URL("../src/index.ts", import.meta.url), "utf8");
    expect(exportedTypeNames(src)).toEqual(EXPECTED);
  });
});
```

Verify `EXPECTED` has 23 entries before running. If the real export list differs from this plan's, the SOURCE wins — update `EXPECTED` and say so in your report.

- [ ] **Step 2: Run and watch it fail**

Run: `npx vitest run test/type-surface.test.ts`
Expected: FAIL — the actual list has 14 entries and lacks the nine.

- [ ] **Step 3: Add the nine exports**

Append type-only exports to `src/index.ts`, following the file's existing style. Use `export type { … }` so nothing is added to the runtime namespace.

- [ ] **Step 4: Run and watch it pass**

Run: `npx vitest run test/type-surface.test.ts` then `npm test` and `npx tsc --noEmit`
Expected: green and clean, 551 tests (550 + this one).

- [ ] **Step 5: Prove the pin catches BOTH directions**

Two separate mutations, each restored after:
1. Add a tenth type export not in `EXPECTED` → the test must go red.
2. Remove one of the nine → the test must go red.

A pin that only catches removals is the weaker half of the job and is what spec §2.7 names.

- [ ] **Step 6: Prove the runtime allowlist did NOT change**

Run: `npx vitest run test/exports.test.ts`
Expected: PASS, unchanged. Type-only exports cannot appear in an `Object.keys` pin. If this test fails, a type was exported as a value — fix it.

- [ ] **Step 7: Re-derive the class rather than trusting this plan**

Spec §6.2 requires it. For each of the 23 exported types, check whether any field, parameter or return type it references is itself unexported. Report what you checked and anything you found. The nine came from one review pass; the point of this step is that the same pass could have missed a tenth.

### Task 3: Emit declarations, and verify them across three resolution modes

**Files:**
- Modify: `tsconfig.build.json`, `package.json`
- Test: `test/exports.test.ts` (extend with a packaging assertion)

**Interfaces:**
- Consumes: Tasks 1 and 2. **Both must be committed first** — declarations emitted before Task 1 would ship literal types, and before Task 2 would ship an incomplete surface.

- [ ] **Step 1: Turn on declaration emit**

`tsconfig.build.json`: add `"declaration": true` to `compilerOptions`.

`package.json`: the `exports` map becomes a conditional object with `types` **ordered before** `default` — condition order is significant and a `types` condition after `default` is never reached:

```json
"exports": {
  ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
  "./package.json": "./package.json"
},
"types": "./dist/index.d.ts",
```

The top-level `types` field is for legacy `moduleResolution: node10` consumers, which do not read the `exports` map; without it their bare root import fails (spec §2.4).
